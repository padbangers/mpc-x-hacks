The user's Akai MPC X runs **Hakai custom firmware** (community mod, MPC app v3.6.x, credits TheKikGen/Ultros/Zangetsu). Base OS: inMusic AZ0x OpenEmbedded/Yocto (`az01` 5.0.17 scarthgap), kernel 6.18 PREEMPT_RT, armv7l.

Key facts for button-remapping work (goal: remap hardware buttons to jump to favourite MPC pages):
- Rootfs `/dev/root` is **read-only** (`/usr` cannot be edited). `/etc`, `/var`, `/srv` are overlay-mounted and writable. `/data` (=`/media/az01-internal`, mmcblk0p7, ~5.9 GB free) and `/sdcard` and external SSD `/media/MPC SSD` are writable — put custom binaries in `/data`.
- MPC app launched via `/usr/bin/az01-launch-MPC` (read-only) which sets `LD_PRELOAD=/usr/lib/hakai_driver.so:/usr/lib/customBufferSizeMPC.so[:mpc_cursor.so]` then execs `/usr/bin/MPC` (50 MB binary).
- `hakai_driver.so` (95 KB, compiled, no external config file found) is a Launchpad-integration + ALSA-MIDI bridge. **Crucially it already implements the exact remap mechanism we need**: intercepts MPC button CCs (`is_mpc_button_cc`, `button_handler`), and injects navigation + touchscreen taps into the app (`inject_touch_event`, `inject_quick_tap`, "TOUCH NAV: Sent N navigation bytes to MPC", "Normale navigatie: U/D/L/R"). But its mapping is compiled-in, oriented to Launchpad + LAUNCH/NOTE/SESSION/CUSTOM buttons — not user-configurable.
- MIDI topology (ALSA seq): buttons/pads come from kernel `client 24: 'MPC X Controller'` ports "MPC Public"(24:0)/"MPC Private"(24:1). The MPC app is `client 129: 'MPC'`. A JUCE virtual-MIDI layer (client 128) sits between. `microKEY2` (Korg, client 16) is also attached.
- **rawmidi `hw:2,0,x` is opened exclusively by the app** — `amidi -d` gives "Device or resource busy", so pure-shell MIDI sniffing is NOT possible. Must subscribe via the ALSA **sequencer** API (non-exclusive) instead.
- On-device tooling: BusyBox shell + ALSA tools (`amidi`, `aconnect`, `aplaymidi`) only. **No python/node/perl and no gcc/cc**. `aseqdump` not installed. `/dev/uinput` exists (touch injection possible).

**INVESTIGATION RESULT (2026-08-06): external ALSA-daemon interception is impossible.** Built/deployed `midimon` (Zig-cross-compiled armhf ALSA-seq monitor, in `/data/hacks/midimon`, links device libasound.so.2). Subscribed to 24:0/24:1/24:2/24:3/16:0/128:2/128:3 and had user press the +/- buttons twice — **zero events captured**. Reason: the physical control surface (buttons/pads/encoders + LEDs) is read by the **MPC app (pid 324) directly from rawmidi `/dev/snd/midiC2D0` ("MPC Public"), bypassing the ALSA sequencer entirely** (app holds midiC2D0 with 3 fds = read + 2 LED-write; nobody holds midiC2D1). Seq-bridge for 24:0 therefore carries no data. Surface USB path: hub 09e8:503a → audio+DFU device 09e8:203a (no MIDI/HID class iface for buttons — they come over midiC2D0). `DeviceControlServer` (pid 321, ALSA client 128 "JUCE") only has /dev/snd/seq open and bridges app<->virtual MIDI, not the panel. `hakai_driver.so` is currently NOT loaded (only customBufferSizeMPC.so in pid 324 maps) — Hakai loads it only if `/dev/disk/by-label/HAKAI` symlink exists.

**HAKAI-WAY RESEARCH (2026-08-06):**
- Hakai itself has NO user-configurable button remap (hardcoded, Launchpad-focused). But Hakai's repo documents the control-surface button MIDI: **+/- data buttons = Minus CC 12 / Plus CC 125 on channel 9** (MPC One table; MPC X likely same protocol — verify on device).
- Hakai's upstream = **TheKikGen MPC-LiveXplore** + repo **TheKikGen/MPCLiveXplore-libs** (default branch `main`). Provides the config/plugin-driven LD_PRELOAD remappers that match exactly the surface-interception technique we proved is the only way: `tkgl_anyctrl(.so)` (replaces the MPC Private/Public rawmidi hw:x,0,0/1 with virtual seq ports so the internal surface becomes visible/injectable), and current `tkgl_midimapper(.so)` (remaps "keys inaccessible in midi learn" via compiled C plugins in `src/tmm-plugins/`; flags `--tkclient`/`--tkport`/`--tkplg`/`--tkdump`/`--tkdumpP`; `tkgl_ctrldump.so` dumps surface controls). Older `src/deprecated/tkgl_mpcmapper.ini` shows the text-config button-code table format (BT_PLUS/BT_MINUS/... per device FORCE/X/LIVE/LIVE2/ONE).
- **Stock MPC firmware itself supports "next/previous track" as a mappable function:** global MIDI mapping via an XML `.xmm` file supports **Target_control=62 "Change track" with RELATIVE CC** (Mapping_control=7 = Rel CC 2's complement) = increment/decrement track. Also Change sequence, mode/screen select, pads, transport. Enable via `.xmm` in `/media/az01-internal-sd/MPC Documents/Midi Learn/` + `MidiLearnEnabled=1` & `MidiLearnPreviousMapping=<path>` in `/media/az01-internal/Settings/MPC/MPC.settings`, then reboot. NOTE: device ALREADY has `New MIDI Mapping.xmm`/`New MIDI Mapping 2.xmm` there. Global mapping consumes *external/mappable* MIDI though — the internal +/- surface CCs aren't external MIDI, so a bridge (anyctrl/midimapper plugin) is needed to expose +/- to the mapping.
- **Recommended path:** anyctrl/midimapper (LD_PRELOAD) to expose the +/- surface buttons as MIDI → bind to relative "Change track" via `.xmm`; OR a tiny midimapper plugin (compile with the session's Zig 0.16 ARM toolchain) that translates +/- directly. CAVEAT: TheKikGen libs are MPC-2.x-era in docs; this device runs a 2026 image (kernel 6.18, MPC 3.6.x) — rawmidi-substitution internals may have shifted; compatibility must be tested. All reversible; still requires the LD_PRELOAD-into-app step.

**★ WORKING END-TO-END (2026-08-06): +/- buttons now change track. ★** Built `shim_remap2.so` (Zig, `/data/hacks/`). Shim can be injected at boot via a systemd drop-in in `/etc/systemd/system` (writable overlay) since `/usr/bin/az01-launch-MPC` is read-only. Reversible, contained risk (worst case: app crash → remove shim). Build toolchain: **Zig 0.16.0** downloaded to the session scratchpad (`zig cc -target arm-linux-gnueabihf.2.31`). Next step if pursued: a *logging* LD_PRELOAD shim to capture the +/- and track-nav MIDI bytes from inside the app. See [[mpc-x-ssh-access]].
